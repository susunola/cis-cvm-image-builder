# ciscvm — Packer × Tencent Cloud CVM × CIS Image Builder

Produce CIS-hardened golden images on Tencent Cloud. A configuration-driven CLI tool that
spins up an ephemeral CVM, applies CIS benchmarks, and captures the result as a custom image —
all from a single `ciscvm.toml` file.

**Linux** images are hardened via the `ansible-local` provisioner, with a build-time
goss audit gate that fails the build if the image is non-compliant. Three backends:

| Backend | Applies to | CIS Engine |
|---|---|---|
| ansible-lockdown | Ubuntu 22/24, RHEL 8/9, CentOS 8/9 | Community Ansible roles, goss audit |
| cis-os (bundled) | TencentOS Server 3/4 | Bundled `cis_engine.py` + `rules.json`, in-role gate |
| ansible (remote) | Windows Server 2019/2022/2025 | Remote Ansible over WinRM, no build-time audit |

> Default: Ubuntu 22.04 LTS, CIS Level 1. See [Profiles](#profiles) for the full list.

## Prerequisites

| Requirement | Details |
|---|---|
| **Python** | ≥ 3.11 (stdlib only — zero pip dependencies) |
| **Packer** | ≥ 1.9 with `packer-plugin-tencentcloud` |
| **Tencent Cloud** | Sub-account with `cvm:RunInstances`, `cvm:CreateImage`, `cvm:DescribeImages`, `cvm:CopyImage`* |
| **Network** | Dedicated VPC + subnet + security group (inbound 22, restricted to build machine egress IP) |
| **Source Image** | Public image ID for the target OS |

\* `cvm:CopyImage` only needed with cross-region copy.

Credentials via environment variables only:

```bash
export TENCENTCLOUD_SECRET_ID=AKIDxxxx
export TENCENTCLOUD_SECRET_KEY=xxxx
```

## Quick Start

```bash
# 1. Bootstrap configuration
python3 ciscvm.py init

# 2. Edit ciscvm.toml with your VPC / subnet / SG / source image ID

# 3. Pre-flight validation (credentials, network, plugins)
python3 ciscvm.py preflight

# 4. Dry-run: render + packer validate
python3 ciscvm.py validate

# 5. Build a hardened image
python3 ciscvm.py build

# Optional: clean up rendered files
python3 ciscvm.py clean
```

| Flag | Default | Description |
|---|---|---|
| `--config <path>` | `./ciscvm.toml` | Configuration file |
| `--workdir <dir>` | `./.ciscvm-build` | Rendered output directory |
| `--quiet` | — | Suppress tool output (validate / build) |

After a successful build the image is available in the target region. Cross-region
replication is automatic if `image.copy_regions` is set.

## Configuration

`ciscvm.toml` is the single source of truth:

```toml
[build]
profile             = "ubuntu22"          # See Profiles table below
region              = "ap-guangzhou"
zone                = "ap-guangzhou-4"
instance_type       = "S5.MEDIUM2"
source_image_id     = "img-xxxxxxxx"      # Replace with actual public image ID
vpc_id              = "vpc-xxxxxxxx"
subnet_id           = "subnet-xxxxxxxx"
security_group_id   = "sg-xxxxxxxx"
associate_public_ip = true

[image]
name_prefix  = "ubuntu-2204-cis"
copy_regions = ["ap-shanghai"]            # [] to disable

[cis]
level        = 1                          # 1 or 2
max_failures = 0                          # Audit failure tolerance (Linux only)
audit_dir    = "/opt/ubuntu22_cis"        # Must match the role's audit output path

[cloud]
secret_id_env  = "TENCENTCLOUD_SECRET_ID"
secret_key_env = "TENCENTCLOUD_SECRET_KEY"
winrm_password_env = "WINRM_PASSWORD"     # Windows only

[meta]
os_tag    = "ubuntu-22.04"
benchmark = "CIS-v2.0.0"
```

## Profiles

### Built-in Profiles

| Profile | OS | Backend | User | Status |
|---|---|---|---|---|
| `ubuntu22` | Ubuntu 22.04 LTS | ansible-lockdown | ubuntu | Stable |
| `ubuntu24` | Ubuntu 24.04 LTS | ansible-lockdown | ubuntu | Preview |
| `rhel8` | RHEL 8 | ansible-lockdown | root | Preview |
| `rhel9` | RHEL 9 | ansible-lockdown | root | Preview |
| `centos8` | CentOS 8 | ansible-lockdown (RHEL 8 role)† | root | Preview |
| `centos9` | CentOS 9 | ansible-lockdown (RHEL 9 role)† | root | Preview |
| `tencentos3` | TencentOS Server 3 | cis-os (bundled role) | root | Stable |
| `tencentos4` | TencentOS Server 4 | cis-os (bundled role) | root | Stable |
| `windows2019` | Windows Server 2019 | ansible (remote) | Administrator | Preview |
| `windows2022` | Windows Server 2022 | ansible (remote) | Administrator | Preview |
| `windows2025` | Windows Server 2025 | ansible (remote) | Administrator | Preview |

† CentOS uses the corresponding RHEL role with `os_check` disabled.

**Stable** — verified end-to-end on Tencent Cloud.
**Preview** — role names and variable prefixes verified against upstream source, but not
yet run end-to-end on Tencent Cloud. Pin `role_version` after validation.

### Switching Profiles

Change one line in `ciscvm.toml`:

```toml
[build]
profile         = "rhel9"
source_image_id = "img-actual-RHEL9-image-id"
```

The SSH user, backend, package manager, and audit directory are carried by the
profile — no other changes needed.

### Adding a Custom Profile

Add an entry to the `PROFILES` dictionary in `ciscvm.py`, then reference its key
in `ciscvm.toml`. Example for a RHEL-family OS:

```python
"almalinux9": {
    "ssh_username": "root",
    "role": "ansible-lockdown.rhel9_cis",
    "role_version": "",
    "audit_dir": "/opt/rhel9_cis",
    "os_tag": "almalinux-9",
    "benchmark": "CIS-v2.0.0",
    "pkg_update": "sudo dnf makecache",
    "pkg_install": "sudo dnf install -y python3-pip git",
    "clean_cmd": "sudo dnf clean all",
    "level1_var": "rhel9cis_level_1",
    "level2_var": "rhel9cis_level_2",
    "boot_pass_var": "rhel9cis_set_boot_pass",
    "os_check_var": None,
    "root_login_rule_var": "rhel9cis_rule_5_2_2",
    "preview": True,
},
```

Three fields must match the role exactly or hardening / audit silently break:

1. **Role name** — exact name on Ansible Galaxy. Fall back to
   `git+https://github.com/ansible-lockdown/<REPO>.git` if unavailable.
2. **Level variable prefix** — `ubtu22cis_` (note: `ubtu`, not `ubuntu`).
   Verify against the role's `defaults/main.yml`.
3. **Audit output directory** — must match where the role writes goss results.

### Switching CIS Level

Set `[cis].level = 2`. Level 2 requires additional partitions
(`/var`, `/var/tmp`, `/var/log`, `/var/log/audit`, `/home` with `nodev`, `nosuid`,
`noexec`). Configure partitions in the source image or via `user_data` before building.

## Architecture

### Build Pipeline

```
Build Machine                              Tencent Cloud
┌─────────────┐                           ┌──────────────────┐
│ ciscvm.py   │── packer build ──────────▶│ Ephemeral CVM    │
│             │                           │                  │
│ ciscvm.toml │                           │ 1. Install ansible
│             │                           │ 2. CIS role (harden)
│             │                           │ 3. Audit gate     │
│             │                           │                  │
│             │◀── image-id ──────────────│ 4. CreateImage    │
└─────────────┘                           └──────────────────┘
```

Three phases executed by Packer on the ephemeral CVM:

1. **Install** — provisions ansible-core and the CIS role inside the instance.
2. **Harden** — `ansible-local` applies the CIS role with remediation.
   Cloud-environment exceptions (boot password, root SSH for RHEL/CentOS, OS check
   for derivatives) are set in the rendered `site.yml`.
3. **Validate** — runs the audit. If failures exceed `cis.max_failures`, Packer
   exits 1 and the image is never created.

### Design Decisions

**`ansible-local` over `ansible`.**
The Packer controller does not need SSH access into the cloud VPC — playbooks and
roles execute inside the instance.

**Cloud-environment exceptions.**
Boot / GRUB password is disabled to prevent lockout. Root SSH login is preserved
for RHEL/CentOS during build. CentOS disables `os_check` to prevent RHEL role abort.
Public-key SSH remains enabled per CIS defaults.

**Build-time compliance gate.**
Goss audit runs after hardening. Missing audit directory → soft-skip with warning;
confirmed path → hard gate, failures above threshold prevent image creation.

**Credentials and governance.**
AK/SK via environment variables only (`sensitive = true` in HCL). Ephemeral instances
are tagged and auto-recycled. Image tags record CIS level, OS, and benchmark.

## TencentOS Server (cis-os Backend)

TencentOS 3/4 use a custom CIS engine (`cis_engine.py` + `rules.json`) instead of
ansible-lockdown. The role is **bundled locally** at `roles/cis_tencentos3/` and
`roles/cis_tencentos4/` — no Ansible Galaxy install required. At build time, the
tool copies the role directory into the rendered workspace.

Key differences from the ansible-lockdown backend:

| | ansible-lockdown | cis-os (TencentOS) |
|---|---|---|
| Role source | Ansible Galaxy | Bundled at `roles/` |
| CIS engine | Community Ansible role | `cis_engine.py` + `rules.json` |
| Audit gate | goss (`verify-cis.sh`) | In-role (`cis_fail_on_findings`) |
| Role install | `ansible-galaxy install` | Copied into workspace |
| Variables | `<role>_level_1/2` | `cis_mode: apply`, `cis_profile: L1/L2` |

Gate behavior: the role sets `cis_fail_on_findings: true` and `cis_min_score: 0` —
if any findings remain after remediation, `ansible-playbook` exits non-zero and
Packer fails the build. No separate verify script needed.

## Windows Server (Preview)

Windows images cannot use `ansible-local` or SSH, and goss is not available.
A different pipeline is rendered for `windows2019` / `windows2022` / `windows2025`:

| | Linux | Windows |
|---|---|---|
| Communicator | SSH | WinRM |
| Provisioner | `ansible-local` (in-VM) | `ansible` (controller → guest) |
| Role install | Inside the CVM | On the controller (before `packer build`) |
| Audit gate | goss | None (post-build verification) |
| Level selection | `<role>_level_1/2` + `--tags` | `win22cis_l1_ms` / `l2_ms` |

### Building a Windows Image

```toml
[build]
profile         = "windows2022"
source_image_id = "img-actual-Windows2022-image-id"

[cloud]
winrm_password_env = "WINRM_PASSWORD"
```

```bash
export TENCENTCLOUD_SECRET_ID=AKIDxxxx
export TENCENTCLOUD_SECRET_KEY=xxxx
export WINRM_PASSWORD='<password meeting Windows complexity policy>'
pip install ansible pywinrm
python3 ciscvm.py preflight && python3 ciscvm.py build
```

The rendered playbook sets `win22cis_ansible_remediation: true`,
`win22cis_create_gpos: false`, and the member-server level variable. GPO and domain
variables are disabled for a standalone golden image. WinRM is preserved.

### Post-build Verification

Since goss does not run on Windows, verify compliance after the image is built:

- Run **Microsoft Policy Analyzer** or **CIS-CAT Pro** against the produced image.
- Use the role's built-in reporting (`win22cis_run_audit` / section-based checks).
